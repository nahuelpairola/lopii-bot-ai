# Feature Inventory — lopii-finance-bot

> What exists, what's planned. Design rationale for these lives in [decisions.md](decisions.md).

### ✅ Implemented

- Server bootstrap: Gin + GORM + Postgres + Goose migrations + webhook bot
- All 6 DB tables created and migrated
- Invitation system: `POST /invitations` → 6-char code + Telegram deep-link (72h, single-use)
- `/start` onboarding: validates invite code → creates user → auto-starts free-text onboarding flow
- **Onboarding via free text** (`onboarding_collect`/`onboarding_confirm` flows, `ClassifyOnboarding` LLM call) — user describes N accounts (name, currency, opening balance) in one message → Call ONBOARDING parses them (monetary balances only, no units/shares) → bot shows summary with Confirmar/Reescribir buttons → on Confirmar, inserts all accounts + opening `transfer` movements atomically via `InsertAccountsWithOpenings` (first account per currency flagged `IsDefault=true`) → receipt + capabilities showcase
- **Admin reset endpoint** (`POST /admin/users/:telegramID/reset`, admin-only) — soft-deletes user's accounts+movements, clears flow state, re-fires onboarding flow
- Health endpoints: `GET /health/internal`, `HEAD /health/external`
- Conversation engine: `Flow`, `TextStep`, `ChoiceStep`, state persisted in Postgres JSONB
- Account repository: full CRUD + default management + unique violation detection
- Subcategory repository: `FindAllForUser`, `DistinctCategoriesForUser`, `FindByCategoryAndSubcategory`, `Insert` + unique violation detection
- ~60 global subcategories across 16 categories + 2 reserved (`Sistema`, `PENDING_REVIEW`), reseeded in `migrations/20260710130000` (replaces the original `20260625234857`)
- Movement GORM model + `InitRepository` + `InsertBatch` (transactional multi-row insert), `FindSimilarForUser` (pg_trgm fuzzy search), `SoftDeleteByIDs`/`ReplaceMovements` (ID-based, atomic DELETE+INSERT), `SumAmountForAccount`
- `handleConversationInput`'s flow-completion dispatch (`handleFlowFinished`, `switch result.FlowName`) — no longer a `"TO_REVIEW"` placeholder for registered flows
- **LLM orchestrator** (`internal/orchestrator/`) — Groq tool-calling HTTP client, 4 call shapes: `ClassifyIntent` (Call 1 router, small/fast model), `ClassifyCreate` (Call 2 CREATE, pro model), `ResolveUpdate` (Call 2 UPDATE, pro model), `ResolveDelete` (Call 2 DELETE, small model)
- **Movement recording (CREATE)** — frictionless by default: a confident Call 2 CREATE classification inserts immediately with a receipt card, no `conversation.Engine` involvement. A genuine gap (PENDING_REVIEW category, or a transfer naming a non-existent account) triggers a guided `ChoiceStep` flow (`movement_create` in `movement_create_flow.go`, every step with a Cancelar bail-out) to fill just that gap before inserting. Atomic multi-leg operations (USD purchase, same-currency transfer, FCI subscription/redemption) share one `transaction_id` — signaled by the LLM via a `group` field, **not** inferred from movement count (the signed-model spec replaces the old `len(rows)>1` grouping, which wrongly lumped independent movements like "pan, medicamentos y carne" into one group; card itemization is now independent expenses too); FCI redemption gain is computed by app code (`SumAmountForAccount` + the destination account's `IsDefault` flag), never by the LLM. USD purchase/sale is now two attributed transfers (`Inversiones | Dólares`, both legs to real accounts, never expense/income) — so ARS balances stay correct and both legs are excluded from cash-flow summaries (`WHERE type != 'transfer'`). Same-currency inter-account moves are `Sistema | Transferencia`.
- **CREATE confirm gate for ambiguous messages** (`movement_confirm_flow.go`) — before ever running Call 2 CREATE, `startMovementCreate` trusts the router's `needs_confirmation` flag alone (Call 1 judged the message too short/ambiguous to trust — e.g. a bare amount with no verb/item/merchant). `true` routes to `movement_confirm_intent` — a single `ChoiceStep` with exactly two options, "✍️ Reescribir mensaje" and "🚫 Cancelar". Doesn't reroute to UPDATE/DELETE and doesn't touch the DB — the bot never guesses the user's real intent, it just asks them to be clearer. (Previously also ran `resolveCandidates` as a second signal even when the router said `false`; dropped — it produced false positives whenever a new CREATE happened to share an amount/description with an unrelated recent movement, second-guessing a router verdict that was already correct)
- **Movement correction (UPDATE)** and **deletion (DELETE)** — share one reference-resolution mechanism (`reference_resolution.go`, `resolveCandidates`): an in-Go token/amount match over a DB window. Default window (no date named) is **recency of entry** — `created_at` within `recencyWindow` (48h) via `FindRecentlyCreatedForUser`, ordered `created_at DESC` — so a movement entered now but dated in the past ("le pagué el asado de ayer") is still a candidate; a mentioned date/range anchors on the business `date` column instead (`FindSimilarForUser`). 0 candidates errors out, 1 proceeds straight to confirm, 2+ shows a picker. UPDATE always requires explicit confirmation (`movement_update_pick` → `movement_update_confirm`, a two-hop flow chain since `conversation.Step`s can't make LLM calls — the second Call 2 UPDATE invocation happens in `proceedToUpdateConfirm`). DELETE is simpler — a single flow whose picker step is skippable straight to a confirm/summary gate once a candidate is known
- `Engine.StartWithData` + `Step.Skip`/`ChoiceStep.SkipIf`/`TextStep.SkipIf` — pre-seed a flow with already-known data (e.g. an LLM classification) and skip past resolved steps
- `pg_trgm` Postgres extension + GIN trigram indexes on `movements.description`/`merchant` (migration `20260702120000`)
- **Movement classification follow-up improvements** (`docs/superpowers/specs/2026-07-04-movement-classification-improvements-design.md`) — 4 shipped:
  - `Movement.Subcategory *subcategory.Subcategory` GORM association (`foreignKey:SubcategoryID`), populated at construction time in `resolveAndInsertMovements`/`fciRedemptionGain`, or via `.Preload("Subcategory")` in `FindSimilarForUser`. Retired the old manual `subcategory_id → name` lookup (`buildSubcategoryIndex` + full `FindAllForUser` fetch + map) that `movementToRow` used to do per call.
  - Confirmation/receipt messages (`msgConfirmMovements`/`movementReceiptLine`, `msgConfirmUpdateDiff`, `msgConfirmDelete` in `internal/controller/messaging/messages.go`) now show category, subcategory, description, and date — not just icon/amount/currency/description.
  - UPDATE/DELETE reference resolution supports a date **range**, not just a single anchor date: `resolveCandidates(userID, message, dateFrom, dateTo)`, `FindSimilarForUser(..., until *time.Time)`. A range ("entre el 27 y el 29") bounds the search on both ends; a single date anchors `since` on the business `date` (no upper cap); with neither mentioned the default is the recency-of-entry (`created_at`, 48h) window, not a `date` cap.
  - Telegram inline-keyboard buttons render as a multi-row grid (`chunkButtons`, `buttonsPerRow = 2` in `internal/controller/messaging/controller.go`) instead of one cramped row — fixes unreadably small category/subcategory/account buttons.
  - `subcategory.Cache` (`internal/subcategory/cache.go`) — in-memory, loaded once at server startup via `NewCache(subcategoryRepo)`, wired into `server.go` in place of the raw repository. No call site outside `server.go` changed signature or behavior.
- **Account creation (ACCOUNT_CREATE)** — Call 1 router recognizes an explicit request to create an account (no movement involved) and starts a dedicated `account_create` flow: name → currency → initial balance → confirm, Cancelar/Atrás at every step. On confirm, creates the `account.Account` (never `IsDefault`) and inserts one opening `transfer` movement (subcategory `Sistema | Saldo inicial`), in the same shape as onboarding, though without transactional atomicity. The account name uniqueness guard (`accounts_user_name_currency_ci_idx`, migration `20260704120000`) is now case-insensitive, hardening this flow and the pre-existing organic account-creation gap-fill in `movement_create_flow.go` alike.
- **Subcategory creation (CREATE_CATEGORY)** — a 5th router intent starts `subcategory_setup`: choose an existing category or name a new one (+ icon), name the subcategory, write a short required description of when it applies, confirm. Cancelar/Atrás at every step via the same `TextStep.EscapeOptions`/`OnEscape` mechanism `account_create_flow.go` already established — no framework change needed. On confirm, inserts the user-scoped `subcategory.Subcategory` row and calls `Cache.Reload()` so it's immediately usable. The description step is the point of the feature, not decoration: it's written straight into `Subcategory.Description`, which is exactly the field `orchestrator.TaxonomyEntry.Description` feeds to Call 2 CREATE as a classification hint — a subcategory with no description is invisible to future auto-classification.
- **DB-backed subcategory icons** — `subcategory.Subcategory.Icon` (column `icon`, migration `20260705120000`, backfilled for all 16 seeded categories from the old static map) replaces the deleted `subcategory.CategoryIcon`/`IconFor`. Every call site now reads `.Icon` off a real row (via `Movement.Subcategory`, `movementToRow`, or a `Cache.FindByCategoryAndSubcategory`/`IconForCategory` lookup) instead of a category-name-keyed static map — required so a user-created category can carry its own icon.
- **`subcategory.Cache` per-user awareness** — `Cache` now splits `global` (the shared seeded taxonomy, one backing slice for every user) from `perUser map[uint64][]Subcategory` (each user's own custom rows). `FindByCategoryAndSubcategory`/`IconForCategory` both take a `userID` and check the user's own rows before falling back to global — needed once subcategory creation could produce two different users' same-named custom category without collision (the DB's own unique index is already scoped by `user_id`).
- **`conversation.Engine` resume gate** — centralized in `Handle`, before any step-specific logic: an idle timeout (10 min since `conversation_states.updated_at`) or a second consecutive step-validation `Retry` shows a generic "¿retomamos o cancelamos?" gate (two reserved `CallbackData` sentinels, `_resume_continue`/`_resume_cancel`) instead of the step's own raw error or a silently stuck conversation. Applies to every registered flow for free — no per-flow code needed. The cancel path sets a dedicated `Result.Data["_resume_cancelled"]` marker, checked once at the top of `handleFlowFinished`, deliberately separate from each flow's own Cancelar convention (there was no single existing convention across the 7 flows to retrofit).
- **Métricas de asertividad LLM (end-to-end)** — tabla `intent_events`, package `internal/metric`. El router loguea un pending por mensaje de movimiento (terminal directo para QUERY/ACCOUNT_CREATE/CREATE_CATEGORY); cada terminal de flow resuelve el outcome vía el último pending del usuario (correlación por WIP=1) y graba en `movement_ids` los ids con los que terminó la operación (create/update insertados, delete borrados) para trazabilidad mensaje→filas. Fire-and-forget. Sin fricción nueva; `confidence` autoreportada y confirmación en CREATE frictionless descartadas a propósito.
- **Signed, account-attributed movements + guard + insufficient-funds gate + LLM-signaled grouping** — the money model made coherent: `resolveAndInsertMovements` runs every CREATE/UPDATE through `normalizeMovements` (`internal/controller/messaging/movement_guard.go`) before insert — sign owned by the app (never the LLM), nil accounts resolved to the currency default, currency/account agreement checked, transfer legs validated as a distinct 2-leg same-currency-sums-to-zero group. `assignTransactionIDs` groups strictly by the LLM-supplied `group` tag (replacing the old `len(rows)>1` heuristic, so independent movements in one message — "compré pan, medicamentos y carne" — are never wrongly grouped). `checkResultingBalances` + `movement_negative_confirm` flow gate a CREATE that would drive an account into or deeper into negative (Registrar igual / Reescribir / Falta registrar algo), CREATE-only. `movementToRow`/`movementReceiptLine` emit `displayAmount` (abs) so the stored sign never escapes storage. Create prompt teaches destination-decides-type + gain-verb + grouping rules. Three test layers: pure guard tests (no DB), mocked-Groq contract test, real-Groq eval (`//go:build llm_eval`, excluded from default CI). Shipped in `docs/superpowers/plans/2026-07-07-signed-account-attributed-movements.md`.

- **Agentic QUERY engine (read-only)** — QUERY is live: `Orchestrator.AnswerQuery` (`internal/orchestrator/query.go` + `client_loop.go`) runs a Groq tool-calling loop (first round `tool_choice:"required"` so the loop always gathers data before narrating, then `"auto"`, `queryModel = openai/gpt-oss-120b` — same as CREATE, cap 3 iterations + a forced `tool_choice:"none"` final narration so the cap yields a summary, not a failure). Model choice validated against real Groq (`query_eval_test.go`): `llama-3.1-8b-instant` was unreliable for the multi-tool loop (deflected without calling a tool under `"auto"`; emitted malformed tool-call syntax under `"required"`); `gpt-oss-120b` answers correctly (accepts the lower 1K RPD, shared with CREATE, in exchange for reliable tool calling). Optional tool params are declared nullable (`["string","null"]`) because the models emit explicit `null` for unset args and Groq 400s a non-nullable schema on that. The messaging controller owns 4 typed read tools (`internal/controller/messaging/query.go`) — `list_categories` (taxonomy + "cuándo usarla" from `Subcategory.Description`), `sum_movements` (grouped totals by category/subcategory/type/month/day/account + filters), `list_movements` (detail rows), `account_balance` (signed per-account) — and the `execute` closure scoped to the user, so invariants live in Go (soft-delete filter, ARS/USD never mixed, `abs` reporting, transfer excluded by default) and the LLM can never emit a wrong number. Repo reads: `movement.SumForUser`/`ListForUser` (+ `MovementQuery`/`CategorySum`). QUERY moved from a direct-terminal metric to pending→resolve (`outcomeQueryAnswered`/`outcomeQueryFailed`). Averages/comparisons/per-day are composed by the loop (narrated arithmetic on tool results; exact-arithmetic tools are the documented upgrade path). Loop tests + 12 executor use-case tests. Shipped in `docs/superpowers/plans/2026-07-08-agentic-query-engine.md`.
- **QUERY robustness follow-up** (`docs/superpowers/plans/2026-07-09-query-robustness.md`) — three fixes: (1) **transient-failure retry** at the single Groq I/O chokepoint `Client.send` (`internal/orchestrator/client.go`) — network/429/5xx only, 3 attempts, exponential backoff (250/500ms, honors `Retry-After` capped 1s), non-429 4xx fails fast; `chatCompletion` + `chatCompletionLoop` both route through it, so every call type inherits it; happy path adds 0ms. (2) **QUERY never asks a clarifying question** — prompt directive makes the loop answer every plausible interpretation at once (killed a real misroute where a one-word follow-up like "Hogar" re-classified as CREATE and stuck `pending`, since QUERY holds no conversation state). (3) **Prettier answers** — prompt: no markdown (raw `**`/`–`), Argentine amount format, friendly dates; plus category **icons** surfaced to the model in `execListCategories` and `execSumMovements` (group_by=category) via `Subcategory.Icon`/`Cache.IconForCategory`. LLM-behavior checks in the `query_eval` test (real Groq, non-CI); deterministic unit tests for the retry and the icon prefixes.
- **QUERY conversation thread** — QUERY now keeps a short, self-expiring memory so follow-ups resolve their referent (e.g. "y la semana anterior?" after "cuánto gasté en automotor esta semana?"). New `query_turns` table + `internal/queryhistory` repo (`Append`/`Recent`); `handleQuery` loads recent turns and `AnswerQuery` prepends them as user/assistant messages before the current question. Tools re-run every call → numbers always fresh; history is textual context only. TTL (default 10 min) and turn limit (default 5) configurable via `[query]` config, env-overridable (`QUERY_HISTORYTTLMINUTES`/`QUERY_HISTORYLIMIT`). Best-effort: a history error runs the query stateless. QUERY only — CREATE/UPDATE/DELETE stay stateless. Plan: `docs/superpowers/plans/2026-07-09-query-conversation-thread.md`.
- **Expense-logging reminders + system→user notification engine** — a daily, activity-aware reminder to log expenses, and the first tenant of a reusable scheduled-notification engine. New `reminders` table (`internal/reminder/`, one row per user, `WindowStartMin`/`WindowEndMin` in minutes since ART midnight, `MidpointMin()` derived fire target, delete==disable) + a rotating Spanish message pool (`PickMessage`, no LLM — "no siempre igual" solved with ~15 hand-written lines, zero recurring cost on an unattended path). Configured entirely by free text via a new `REMINDER_SET` router intent → a **deterministic** `reminder_setup` `ChoiceStep` flow (`internal/controller/messaging/reminder_setup_flow.go`) — time-band presets, a custom-window text step (`parseWindow`, whole 24h hours only), or "apagar" — no Call 2, no LLM parsing beyond the router, no confirm gate (frictionless, like ACCOUNT_CREATE/CREATE_CATEGORY). Consulting the reminder ("¿a qué hora me recordás?") is a 5th QUERY tool, `get_reminder`, not a new flow. Delivery is `internal/notifier.Sweeper` — an in-process `time.Ticker` goroutine (default every 5 min, `[reminders].sweepIntervalMinutes`) started alongside `tgBot.StartWebhook`, not an external cron (the bot already runs 24/7 single-instance, so a ticker is zero new infra and can't double-send). Each tick calls `sweepReminders`: skip if not yet past the window midpoint, skip if the user already has any movement logged today (`FindRecentlyCreatedForUser`, no new movement-repo method needed), skip if already reminded today (`last_reminded_on` guard), else send + mark. `Sweeper.send` is an injected field — the one asset a future notifier (Cafecito prompt, weekly summary, a segmented broadcast) reuses; each notifier's candidate query/condition/cadence stays its own, never generalized into a registry or a polymorphic table. Spec: `docs/superpowers/specs/2026-07-09-expense-reminders-design.md`. Plan: `docs/superpowers/plans/2026-07-09-expense-reminders.md`.
- **Onboarding offers the reminder** — a bullet added to `msgCapabilitiesShowcase` ("⏰ Recordatorio: ...") for passive visibility, plus an explicit `onboarding_reminder_offer` `ChoiceStep` flow (single step, Sí/No, no Cancelar) chained right after the showcase via the same `startFlowIfNotBusy` mechanism `onboarding_collect` already uses to chain into `onboarding_confirm`. "✅ Dale" hands off to `startReminderSetup` verbatim — no separate window-picking logic; "🙅 Ahora no" is a no-op. No tracking of whether a user was ever offered (a decliner can still ask later via free text). Spec: `docs/superpowers/specs/2026-07-09-expense-reminders-design.md` (Annex A). Plan: `docs/superpowers/plans/2026-07-10-onboarding-reminder-offer.md`.
